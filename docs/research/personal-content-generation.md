# Generación estructurada de contenido personal con OpenRouter

Investigación para [Investigar generación estructurada con uno o varios agentes en OpenRouter](https://github.com/soloidx/python-tutor/issues/74), dentro del [Mapa: generador conversacional de contenido personal](https://github.com/soloidx/python-tutor/issues/73). Consultado el 10 de noviembre de 2026 UTC. Documento de planificación en rama desechable; no propone fusionarse ni implementa el generador.

## Resultado y alcance

Los dos enfoques son técnicamente posibles: un agente que conversa, genera y repara por etapas, o varios roles que intercambian propuestas. Ninguno elimina los límites del modelo ni la validación local. **Generar por partes y reintentar partes no exige varios agentes**. Esta es una inferencia de las capacidades de invocación/herramientas y de las alternativas de orquestación documentadas; no es una medición de calidad. LangChain también advierte que una tarea compleja puede resolverse con un solo agente. [Invocación, herramientas y estructura](https://docs.langchain.com/oss/javascript/integrations/chat/openrouter), [orquestación multiagente](https://docs.langchain.com/oss/javascript/langchain/multi-agent).

La arquitectura permanece abierta. El requisito confirmado es contenido privado del estudiante en este navegador, usando la misma clave y modelo del tutor, Python ejecutable en el entorno actual y sin cuentas ni sincronización. El flujo conserva dos aprobaciones: aclaración → aprobar generación → revisar contenido y pedir cambios → aprobar incorporación → Learning paths. Reutilizar un curso original conserva identidad y progreso; generar uno distinto crea contenido propio. Son decisiones de producto del [mapa](https://github.com/soloidx/python-tutor/issues/73), no capacidades garantizadas por OpenRouter. Se leyó también el `GLOSSARY.md` vigente del checkout principal, todavía sin seguimiento en Git al investigar; no se añadió ni modificó.

## Capacidades verificables y sus límites

| Área | Hecho y fuente primaria | Consecuencia para este producto (inferencia o propuesta) |
| --- | --- | --- |
| Esquema nativo | Chat Completions admite `response_format: {type: "json_schema", json_schema: {name, strict, schema}}`. El soporte es **por endpoint** y puede cambiar; `strict` tiene distinta fuerza y subconjuntos de JSON Schema según proveedor. [OpenRouter structured outputs](https://openrouter.ai/docs/guides/features/structured-outputs) | Comprobar el modelo elegido y sus proveedores; validar también localmente. No prometer que todo modelo del tutor genera cursos con el mismo modo. |
| Routing | `provider.require_parameters: true` restringe a endpoints compatibles. `only` y `allow_fallbacks` permiten controlar proveedores; las restricciones pueden dejar cero endpoints. [Provider routing](https://openrouter.ai/docs/guides/routing/provider-selection) | Evitar degradación silenciosa del esquema. Un fallo de compatibilidad debe ser explícito; no cambiar de modelo sin autorización. Fijar proveedor para comparar resultados, si está disponible. |
| LangChain instalado | `withStructuredOutput` dispone de `jsonSchema`, `functionCalling` y `jsonMode`; `bindTools` enlaza definiciones. [Integración JS](https://docs.langchain.com/oss/javascript/integrations/chat/openrouter) | Son mecanismos de transporte/extracción; las etapas, límites, aprobaciones y persistencia necesitan lógica de aplicación. |
| Selección del modo | En **0.4.22**, el método automático usa el perfil estático integrado; un ID ausente devuelve perfil vacío. Pedir `jsonSchema` explícito sin perfil compatible lanza error local. Con routing multimodelo el modo automático usa function calling. [Fuente distribuida 0.4.22](https://unpkg.com/@langchain/openrouter@0.4.22/dist/chat_models/index.js), [selector](https://unpkg.com/@langchain/openrouter@0.4.22/dist/utils/structured_output.js) | El catálogo vivo de OpenRouter y el perfil empaquetado pueden discrepar. Verificar el ID exacto; probar el payload real antes de elegir implementación. No asumir actualización automática por consultar `/models`. |
| Parser local | Core **1.3.5** valida Zod/Standard Schema; con JSON Schema plano usa parser JSON sin validar el esquema. `includeRaw` puede devolver `parsed: null` al fallar. [Código distribuido](https://unpkg.com/@langchain/core@1.3.5/dist/language_models/structured_output.js) | Siempre comprobar estado y ejecutar validadores de dominio; JSON parseado no significa curso válido. |
| Herramientas | El modelo propone tool calls; el cliente ejecuta y devuelve resultados. Tools y llamadas paralelas dependen del modelo. [Client tools](https://openrouter.ai/docs/guides/features/tool-calling) | Limitar a funciones concretas: consultar catálogo, comprobar borrador, etc. El modelo no debe concederse aprobación ni publicar/incorporar por su cuenta. Paralelismo de tools no equivale a varios agentes. |
| Contexto y salida | El catálogo expone `context_length`, `supported_parameters`, `top_provider.max_completion_tokens` y precios. Son metadatos consultables, no un tamaño universal. [API Models](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties) | Contar historial, instrucciones, esquema, catálogo enviado y resultado dentro del presupuesto. Ventana grande no implica salida igualmente grande. Preferir unidades acotadas en el experimento; ensamblar y validar el curso completo antes de incorporarlo. |

El soporte del endpoint no homogeneiza los esquemas: OpenAI documenta un subconjunto, campos requeridos y `additionalProperties: false`; también rechazos y respuestas incompletas. Anthropic distingue JSON de salida y strict tools, con limitaciones propias. Un esquema admitido directamente por el proveedor no demuestra que ese modelo tenga el mismo soporte por cualquier endpoint OpenRouter. [OpenAI](https://developers.openai.com/api/docs/guides/structured-outputs), [Anthropic](https://platform.claude.com/docs/en/build-with-claude/structured-outputs).

### Streaming, cancelación, reintentos y coste

OpenRouter transmite SSE y también permite structured outputs en streaming. Los fragmentos son provisionales; el JSON final puede no llegar. Abortar la conexión solo detiene procesamiento/facturación en proveedores compatibles: la documentación incluye OpenAI/Anthropic como compatibles y Google/Groq como no compatibles actualmente. Un HTTP 200 puede preceder un error SSE; no demuestra éxito. [Streaming y cancelación](https://openrouter.ai/docs/api_reference/streaming), [salidas estructuradas](https://openrouter.ai/docs/guides/features/structured-outputs).

**Propuesta:** registrar por unidad intento, versión de borrador, estado final, motivo de terminación y error; ignorar respuestas de una versión anterior después de cancelar o editar. Tratar truncamiento, rechazo, JSON incompleto, timeout y error de validación como resultado fallido, sin insertar partes en Learning paths. Reintentar una unidad es otra petición, no continuación exactamente una vez. Un borrador completo pendiente puede coexistir con el catálogo activo sin afectarlo. Es una estrategia candidata, no comportamiento implementado.

OpenRouter documenta errores de credenciales, créditos, límites y disponibilidad; algunos incluyen `Retry-After`. Un 402 sin indicación temporal no se resuelve con bucle de reintentos. **Propuesta:** reintentos limitados con espera para fallos transitorios; corrección de entrada/esquema para errores permanentes y reparación acotada para validación. Separar reintento de transporte, reparación LLM y fallback del proveedor evita multiplicarlos inadvertidamente. [Errores](https://openrouter.ai/docs/api_reference/errors-and-debugging), [límites de clave y concurrencia](https://openrouter.ai/docs/api_reference/limits).

No hay presupuesto ni benchmark verificado. Estimar por suma de tokens de entrada/salida de **todas** las llamadas, precios vigentes, herramientas y reparaciones; comparar contra uso/coste devuelto cuando exista. Más roles con el mismo modelo repiten contexto y añaden llamadas, aunque podrían reducir reparaciones: esa posible compensación es una hipótesis. La concurrencia comparte la misma clave y sus límites. El transporte actual descarta usage aunque el adaptador lo expone. [Precios por modelo](https://openrouter.ai/docs/api/api-reference/models/list-all-models-and-their-properties), [usage del adaptador](https://unpkg.com/@langchain/openrouter@0.4.22/dist/converters/messages.js), [límites](https://openrouter.ai/docs/api_reference/limits).

## Comparación para decidir, sin elegir arquitectura

Las filas de diseño siguientes son alternativas razonadas a partir de las APIs anteriores; las ventajas de calidad y rendimiento quedan por medir.

| Criterio | Un agente con etapas y validadores | Exploración + generación + revisión LLM, con validadores |
| --- | --- | --- |
| Misma clave y modelo | Una configuración, varios turnos si hace falta. | Cada rol puede usar exactamente esa configuración; no requiere modelos diferentes. |
| Contexto | Reutiliza diálogo/objetivo; debe resumir o seleccionar contexto. | Cada rol puede recibir un contexto menor; hay que transmitir restricciones e identidad sin perderlas. |
| Curso completo | Puede generar por tema y ensamblar. | Puede distribuir temas; necesita reconciliar prerrequisitos, duplicados y estilo. |
| Corrección | Validadores más revisión humana. | Los mismos validadores más crítica probabilística; otro LLM no certifica respuestas ni checks. |
| Fallos parciales | Reintentar una unidad y reconstruir borrador. | Además fallan traspasos y agregación; una parte aprobada por otro agente sigue sin autorizar incorporación. |
| Latencia/coste | Menos llamadas de coordinación como hipótesis inicial. | Paralelizar unidades podría reducir espera, con más concurrencia/contexto y límites compartidos. |
| Control | Lógica de etapas sencilla o tools acotadas. | Coordinador explícito, límite de pasos/delegaciones y contratos por rol. |
| Dependencias | Adaptador actual más lógica de aplicación. | También puede orquestarse con JavaScript; LangGraph u otro harness sería una dependencia opcional por evaluar. |

LangChain presenta los agentes especializados como una opción de gestión de contexto, no una garantía de superioridad. No se ha demostrado que sus harnesses adicionales compilen o persistan adecuadamente en este Vite/browser; esta investigación solo confirma el adaptador ya usado. [Multi-agent JS](https://docs.langchain.com/oss/javascript/langchain/multi-agent).

OpenRouter ofrece además **Subagent** y **Advisor**, herramientas de servidor beta que realizan llamadas internas con coste/latencia adicionales. Son una tercera ubicación posible de la coordinación; no hacen local la generación y no están integradas aquí. Sus recetas proponen modelos baratos/distintos: eso no autoriza sustituir el modelo del estudiante. El soporte y payload de esas herramientas requieren su propio spike antes de usarlas con este adaptador. No se adoptan sus cifras promocionales de ahorro como evidencia. [Subagent](https://openrouter.ai/docs/cookbook/building-agents/subagent-server-tool), [Advisor](https://openrouter.ai/docs/cookbook/building-agents/advisor-server-tool).

## Qué puede validar el navegador

El contrato actual valida estructura, IDs, pertenencia a rutas, opciones/answerId, discriminación code/choice y campos de temas/ejercicios. Integridad SHA-256 acredita bytes, no verdad pedagógica. El catálogo público se activa completo; esto es evidencia útil para una incorporación personal atómica, no una decisión de reutilizar su almacenamiento/publicación. No se propone publicar contenido privado en el repositorio editorial. [Contrato vigente](https://github.com/soloidx/python-tutor/blob/4b640b05a2afe075f010dc4dac4f7a96b3556e6d/docs/catalog.md).

**Propuesta de niveles separados:** (1) validar estructura y referencias con el contrato; (2) ejecutar ejemplos y una solución de referencia generada en el Pyodide exacto; comprobar que pasa el check y que variantes incorrectas relevantes fallan; (3) revisar coherencia, ambigüedad y progresión con una rúbrica y, opcionalmente, otro LLM; (4) aprobación del estudiante para incorporar. La solución de referencia no es hoy un campo del contrato público: sería material temporal de validación por definir. Ni pasar muestras ni acordar dos LLM demuestra que un check acepte todas y solo las soluciones correctas.

El worker actual ejecuta código y después `bool(check)` en su namespace, sin `input()`; `usePython` lo termina a los diez segundos. Pyodide 0.28.3 no equivale a Python de escritorio: faltan módulos y capacidades de procesos/sockets, y las peticiones siguen las políticas del navegador. Recomendar pruebas en un worker separado del ejercicio activo para no modificar su progreso/runtime. Un worker evita bloquear la UI, **no constituye aislamiento de seguridad completo** para ejecutar código generado; puede realizar red y el puente Python/JS exige revisar capacidades antes de automatizar validaciones. [Worker local](https://github.com/soloidx/python-tutor/blob/4b640b05a2afe075f010dc4dac4f7a96b3556e6d/public/python-worker.js), [límites locales](https://github.com/soloidx/python-tutor/blob/4b640b05a2afe075f010dc4dac4f7a96b3556e6d/src/usePython.js), [compatibilidad Pyodide](https://pyodide.org/en/0.28.3/usage/wasm-constraints.html), [capacidades de workers](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers).

## Privacidad, credenciales y persistencia local

Sin backend propio es viable reutilizar `fetch` del adaptador desde el navegador con la clave aportada por el estudiante. La clave sigue accesible al JavaScript de ese origen y a quien controla el navegador; no puede volverse un secreto de servidor mediante bundling. Mantenerla fuera de mensajes, archivos generados, logs y tool results; pasar solo la información necesaria a cada rol. Es una consecuencia de la implementación y del almacenamiento por origen. [Adaptador fetch](https://unpkg.com/@langchain/openrouter@0.4.22/dist/chat_models/index.js), [almacenamiento de acceso](https://github.com/soloidx/python-tutor/blob/4b640b05a2afe075f010dc4dac4f7a96b3556e6d/src/tutorAccess.js), [same-origin](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy).

“Privado por estudiante” no significa inferencia local: objetivo, mensajes y contenido enviado atraviesan OpenRouter y proveedores. OpenRouter declara excepciones legales/de seguridad a su política de retención; `data_collection: deny` y `zdr` restringen routing, con matices sobre Safety Retention y herramientas. No garantizan ausencia de todo procesamiento/retención. Más roles pueden enviar copias adicionales. [Política OpenRouter](https://openrouter.ai/docs/guides/privacy/data-collection), [controles por petición](https://openrouter.ai/docs/guides/routing/provider-selection).

Web Storage tiene cuotas pequeñas; IndexedDB ofrece almacenamiento mayor gestionado por el navegador, pero también puede fallar o ser eliminado. No hay garantía de continuidad tras borrar datos/perfil. **Propuesta:** probar quota/recarga, conservar la última versión válida y persistir checkpoints del borrador sin activar contenido parcial. Elegir localStorage frente a IndexedDB y el formato de exportación/recuperación sigue abierto; cerrar la pestaña no crea trabajo durable en segundo plano. [Cuotas y expulsión](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

## Experimento mínimo sugerido, no ejecutado

1. Preparar dos briefs pequeños con el mismo tamaño: uno que reutiliza un curso original y añade otro, y otro que genera un curso nuevo. Ambos incluyen code, choice, prerrequisitos, ejemplo y checks; acotar temas/ejercicios para que los brazos sean comparables. Usar el modelo exacto elegido por el estudiante, la misma clave y mismo endpoint/política cuando sea posible. Si falta capacidad, registrar incompatibilidad sin sustituirlo.
2. Probar primero un esquema pequeño con esa pareja modelo/proveedor, modo explícito y `require_parameters: true`. Capturar payload sin secretos, versión del paquete, soporte vivo, esquema aceptado/rechazado y finish reason. Comprobar diferencias del perfil estático. Esto es una prueba de integración, no un benchmark de enseñanza.
3. Comparar A: un rol que aclara/genera/repara por unidades; B: roles explorador, generador y revisor con el mismo modelo. Mantener iguales presupuesto máximo de llamadas/tokens, validadores y aprobaciones. Ejecutar varias repeticiones, anotando que una muestra pequeña no generaliza.
4. Registrar latencia total, tiempo hasta primer resultado útil, tokens/coste disponibles, unidades regeneradas, errores estructurales, checks que fallan y observaciones humanas sobre objetivos y ambigüedad. Evaluar crítica LLM como sugerencias y verificar sus afirmaciones; no usar acuerdo entre modelos como aprobación automática.
5. Inyectar corte de stream, truncamiento, cancelación, respuesta tardía, 429/402, esquema inválido, referencia inexistente, worker bloqueado y fallo de almacenamiento. Verificar que no cambia el contenido activo/progreso hasta aprobación y commit completo, y que reintentar no duplica cursos. Probar cambio de configuración y recarga con borrador pendiente.
6. Presentar resultados al usuario para elegir arquitectura, política de compatibilidad y límites. Antes de ejecutar cualquier llamada real, concretar tamaño y tope de gasto del experimento; aquí no se hicieron completions ni se usó la clave del estudiante.

Las pruebas propuestas aún no prueban calidad, costes ni compatibilidad real del futuro generador. Esta investigación resuelve la disponibilidad y las restricciones conocidas, dejando la elección arquitectónica y los criterios de aceptación pedagógica a los tickets de decisión del mapa.
